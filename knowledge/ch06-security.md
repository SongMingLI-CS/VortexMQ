# 第六章 安全与多租户

> 接 [第五章](ch05-distributed.md)。本章不是密码学课。目标只有两个：A 公司看不见 B 公司；一张坏请求不能把进程打死。
>
> 编号 46–52。上一章：[分布式](ch05-distributed.md) · 下一章：[算法](ch07-algo.md)

多租户 = 多家互不相识的调用方共用一套 VortexMQ。隔离必须由服务端强制，不能靠「请调用方不要传别人的 ID」。

---

## 46. API Key 与 bcrypt（熟练）

### 为什么不用「用户名+密码登录」

本项目的调用方是程序（curl、压测、别的后端），不是浏览器里的人。程序适合持有一把长随机钥匙，放在请求头里，每次带着。没有 session cookie，没有跳转登录页。

钥匙格式：`vxk_` + `secrets.token_urlsafe(32)`。前缀给人看；后面是不可预测字节（第 5 条）。

### 为什么不能把钥匙明文存进数据库

数据库备份会泄露、SQL 注入会泄露、日志会打出 SELECT *。明文钥匙等于把每家公司的大门钥匙复印进一本可能被拿走的通讯录。

**哈希：** 单向搅拌。从哈希推不回钥匙（按设计）。校验时用客人出示的明文再搅拌一次，看结果是否和库里那一串匹配。

**bcrypt：** 一种故意很慢、并且自带随机盐的哈希。慢，是为了让「猜一百万把钥匙」在时间上不可行。盐，见下一条。

签发：`python -m app.cli create-tenant default` 打印明文 **一次**。库里从一开始只写哈希和前缀。终端里那一行要立刻存进密码管理器。丢了只能 `--rotate`：旧钥匙立刻失效，正在用旧钥匙的脚本会全部 401。这是 intentionally 痛苦，避免「两把钥匙同时有效」的混乱（本项目不做多把并存）。

### 校验放线程池

见第 6 条。每个带 Key 的 HTTP 都会 bcrypt 一次。压测时 API CPU 会明显花在这上面，是安全预算，不是漏优化。

### 停下来想

能不能用 SHA-256 代替 bcrypt？SHA-256 太快，显卡可以每秒试海量候选。钥匙够长时风险下降，但行业惯例对「需要存储的口令类秘密」仍用慢哈希。本项目跟惯例。

## 47. 带盐哈希不能当查找键（深入）

### 盐是什么

同一把钥匙，不加盐时，哈希结果永远一样。攻击者预先算好常见钥匙的哈希表（彩虹表），对照库里的哈希就能反查。

**盐：** 搅拌前掺一笔随机数。同一把钥匙每次 bcrypt 结果都不同。库里存的字符串其实包含了盐和哈希，校验函数会把盐取出来再用。

### 因此不能 SQL 等值查找

错误想法：

```sql
SELECT * FROM tenants WHERE api_key_hash = crypt(:用户传来的明文);
```

bcrypt 每次 crypt 盐不同，等值永远对不上（除非用数据库提供的特殊 crypt 函数并取出原盐，那是另一套）。本项目在 Python 里 verify，必须 **先找到那一行** 再 verify。

找不到行怎么办？总不能对所有租户逐个 verify（租户一多，请求会扫全表，还帮攻击者做 CPU 放大）。

**前缀索引：** 存明文的前 24 个字符在 `api_key_prefix`，有唯一索引。流程：

```text
1. 明文太短 → 直接失败
2. SELECT WHERE api_key_prefix = 前24位  → 最多一行（唯一）
3. 没有这行 → 401
4. bcrypt.verify(明文, 行哈希) → 失败则 401
```

前 24 位包含 `vxk_` 和一部分随机。碰撞时签发会重试生成（最多 8 次）。前缀 **单独不能当凭证**：知道前 24 位没有后半段，verify 仍失败。

### 停下来想

前缀存在库里，备份泄露会怎样？攻击者得到「钥匙长什么样的开头」和哈希。仍要暴力猜后半段，且每次猜都要 bcrypt。比泄露明文好得多，但前缀缩短了搜索空间。24 位是「能定位」和「少泄露」之间的折中。轮换钥匙会同时换前缀。

## 48. 身份只来自 Header（熟练）

### 身体会撒谎

JSON 身体由调用方完全控制。若 Schema 接受 `tenant_id`，恶意调用方会写别人的 UUID。服务端若信它，任务会进别人名下，或查询会读别人的行。

Header `X-API-Key` 也是调用方控制的——他可以偷别人的钥匙。但那是「偷了钥匙」，不是「口头声称我是谁」。安全模型是：**持有钥匙 = 是这个租户**。没有第二因素。保护好钥匙（不进 git、不进日志）是运维责任。

`get_current_tenant` 只认 Header。`TaskCreateRequest` 没有 tenant 字段。Worker 消息里虽有 tenant_id，那是服务端自己 XADD 时写入的，仍要和第 52 条交叉验证。

### 停下来想

把 Key 放在 URL 查询串 `?api_key=` 为什么更糟？URL 会出现在浏览器历史、反向代理日志、出错时的 referer。Header 也会进某些日志，但少一条常见泄露路径。仍不要在应用日志里打印 Header 全值。

## 49. 查询一律带租户谓词（熟练）

### 谓词就是 WHERE 里的条件

```sql
SELECT ... FROM task_records
 WHERE task_id = :tid AND tenant_id = :my_tenant
```

只写 `task_id` 时，猜到 UUID 就能读别人的结果（UUID 难猜，但日志、屏幕分享会泄露）。两个条件同时成立才返回行。Python 里 `get_task_for_tenant`。找不到统一 404。

### 404 而不是 403

403 的语义是「资源在，你没资格」。攻击者可以靠 403/404 的差别确认「这个 ID 存在」。404 把「没有」和「不是你的」合成一种回答，减少探测。对合法用户，用错钥匙看自己的任务也会 404，需要他们检查 Key——这是有意的体验代价。

工作流 XCom 读上游快照时同样强制 `tenant_id=`，防止图被篡改成「依赖另一个租户的任务 ID」从而把别人的 result_data 注入进来。

### 停下来想

Worker 内部 `get_task_with_tenant` 按 task_id 读且不带租户条件，随后用消息里的 tenant_id 交叉验证。为什么 Worker 不走 HTTP 那套 get_task_for_tenant？因为它不是租户调用方，它是内部执行者。仍有第 52 条，不是裸读。

## 50. Payload 体积上限（熟练）

### OOM

进程能用的内存有限。一个 500MB 的 JSON 进来，Pydantic 解析、再存 JSONB、Worker 再读出，可能把 API 或 Worker 打到被系统杀掉。杀掉的是整个进程， **所有租户** 一起挂。这是拒绝服务。

256KiB 是武断但明确的上限：够放一封邮件的元数据，不够放视频。超限 413。计算按 `json.dumps` 后的 UTF-8 字节数，不是 Python 对象在内存里的大小（后者更大）。有人用大量空格刷体积也会被拦住。

### 停下来想

256KiB 拦不住「每秒一万个合法小请求」。那是另一类滥用（第 6 条末尾），需要限流、配额，本项目没有。体积上限只覆盖「单请求撑爆内存」。

## 51. 系统保留命名空间（熟练）

### 注入

工作流在子任务 payload 里写入：

```json
{
  "用户自己的字段": "...",
  "_vortex_sys": {
    "upstream_results": {
      "父任务UUID": { "output": "..." }
    }
  }
}
```

若提交时允许用户自己带 `_vortex_sys`，他可以伪造上游结果，下游业务若盲目信任，会被骗。门口直接拒绝顶层这个键。

系统写入时用 `VORTEX_SYS_KEY` 常量，避免魔法字符串散落。用户业务字段不要用这个名字。嵌套在用户字段内部的 `_vortex_sys` 不会被顶层检查拦——约定是顶层保留。下游应只读顶层系统栏。

`flag_modified` 见第 17 条，漏了注入会丢。

### 停下来想

为什么不把上游结果放在单独列而要塞进 payload？单独列也行。塞进 payload 让模拟执行和未来的业务函数只面对一个 dict。代价就是必须保留键。两种设计都可以，本项目选了后者。

## 52. Stream tenant_id 与行交叉校验（熟练）

### 皮带和吊裤带

键已经是 `{tenant_id}:...`，理论上消息不会跑到别人车道。仍然校验：

```text
消息字段 tenant_id == 行上的 tenant_id
否则 ACK + 警告日志
```

防御：

- 将来有人误把全局 Stream 写回来
- 手运维 XADD 填错
- 成员格式兼容期的脏数据

Worker 是内部组件，但仍是攻击面：能向 Redis 写消息的人，不应因此获得执行别人任务的能力。执行权最终以 **行上的租户** 为准。

越权时选择 ACK：否则脏消息堵 PEL。并打 warning，方便发现谁在乱写 Redis。

### 停下来想

若攻击者能写 Redis，他已经很接近系统内部。这条校验不是「Redis 暴露给公网也安全」的理由。Redis 必须在内网。校验是纵深防御的一层，不是边界本身。

---

## 第六章小结

- 钥匙只打印一次，库里只有 bcrypt；前缀用来找行，不能当凭证。
- 身份来自 Header，查询带租户谓词，跨租户当 404。
- 体积上限保进程；保留键防伪造 XCom；消息租户和行再对一次。
